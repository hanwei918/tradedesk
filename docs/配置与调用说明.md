# 配置与调用说明

完整的配置导出见 `app/config/agents.json`，运行 `python3 tools/export_config.py` 生成。里面包括 6 个智能体的角色、任务、交互方式和完整提示词，4 个工作流的每一步，知识库绑定，以及模型参数。

## 1. 智能体配置

| 智能体 | 提示词文件 | 任务 | 交互方式 |
|---|---|---|---|
| 询盘分析员 | `prompts/understand_inquiry.md` | 抽取买家画像、需求、质量信号、与资料卡的冲突，每条都要带询盘原文 | 收到新询盘时自动触发 |
| 外贸业务员 | `prompts/reply_inquiry.md` | 用买家语言写阿里国际站 RFQ 回复，同时写一份中文内部备忘 | 多轮：业务员用中文提修改意见 |
| Amazon 运营 | `prompts/listing_amazon.md` | 中文资料 → Amazon 美国站英文 Listing | 多轮 |
| TikTok 内容运营 | `prompts/listing_tiktok.md` | 中文资料 → TikTok Shop 墨西哥西语种草脚本 | 多轮 |
| 合规审核员 | `prompts/compliance_review.md` | 按"模型判断"类规则审核，必须给出规则编号和原文片段 | 每次生成后自动触发 |
| 主图审核员 | `prompts/vision_review.md` | 看主图，判断文字宣称、徽章、道具、是否实拍、产品是否只出现一次；必须写出看到了什么 | 在商品看板上传或选择主图后触发 |

**模型设置**：
- 模型可以在 `app/.env` 里配置，有两种接口：
  - OpenAI 兼容的 Chat Completions，比如赛事赞助的 Tokenhub（`https://api.tokenhubcloud.net/v1`）；
  - Claude Messages API，走官方 SDK；也可以经 Tokenhub 调用（地址 `https://api.tokenhubcloud.net`，不带 /v1，key 按 Bearer 发送）。
- 模型名因 key 而异："模型设置"里的「查可用模型」会调用 `/v1/models` 列出这把 key 能用的模型。
- 经 Tokenhub 调用 Claude 时，只发送模型、系统提示、消息和 max_tokens；effort 和服务端 fallback 只在官方接口上使用，避免网关不认识这些字段而拒绝请求。
- 演示录制用的是 `claude-opus-5-5`，effort 设为 medium，并开启了服务端 fallback。
- 每次调用都要求模型只输出 JSON。

**知识库绑定**：
- 生成时：把对应平台、对应市场的规则摘要放进提示词。
- 审核时：只把"模型判断"类规则交给审核员。
- 代码校验时：用"正则 / 长度"类规则，加上产品资料卡。
- 买家语言决定市场：西班牙语对应墨西哥，额外加上 NOM 和商务礼仪规则；英语对应美国。

## 2. 一次完整调用的标注（工作流 A，美国热水壶询盘，第 1 轮）

数据来自 `app/logs/calls.jsonl`，完整结果在 `docs/demo-runs/INQ-US-01-round1.json`。

**触发条件**：业务员在"询盘回复"页选中询盘，点"理解 → 生成 → 校验"。日志里的 `trigger` 字段是"收到新询盘"。

**输入**：
- 询盘原文（虚构）："…Need it UL listed and BPA free… Please quote FOB Ningbo by air, we need goods in 20 days. Payment: we usually pay 100% 60 days after delivery."
- 业务员意图："报 FOB 宁波海运价，MOQ 500 没问题，付款要 30% 定金，交期 35 天。UL 我们没有。"
- 工厂与产品资料卡 `data/products.json` 里的 `KET-17S`

**调用过程**：

| 步骤 | 角色 | 输入 | 返回 | 用量（tokens，输入 / 输出） |
|---|---|---|---|---|
| ① 理解 | 询盘分析员 | 询盘 + 资料卡（1,846 字符） | 买家画像、需求、质量信号，以及 5 条冲突（UL、BPA、付款、交期、运输方式），每条都附询盘原文 | 1,637 / 2,115 |
| ② 生成 | 外贸业务员 | 询盘 + 分析 + 资料卡 + 意图 + 阿里平台规则摘要（5,658 字符） | 英文回复 + 中文内部备忘 + 4 条派给其他岗位的任务（每条挂询盘原文）+ 写法说明 | 4,419 / 2,781 |
| ③ 代码校验 | — | 回复全文 | 认证、材料宣称、价格底线、MOQ、交期、付款、FOB 运输方式等检查，结果为 0 条 | 不调用模型 |
| ④ 模型审核 | 合规审核员 | 8 条规则（阿里 ALI-01~03、Incoterms INC-01~05）+ 资料卡 + 回复（5,786 字符） | 1 条提示，规则编号和原文都通过出处守卫，丢弃 0 条 | 3,424 / 703 |
| ⑤ 反馈 | — | — | 风险等级：**黄 · 需人工确认** | — |

**返回的那条提示**：
- 原文："1,200 pcs: USD 9.80/pc, FOB Ningbo (sea freight, Ningbo-Zhoushan port)."
- 问题：1,200 台海运基本是集装箱，FCA 比 FOB 更合适
- 依据：**INC-02**，“FCA (Free Carrier) is the more appropriate Incoterms® rule.”（academy.iccwbo.org）
- 建议：在报价后补一句"如需要也可报 FCA Ningbo"，是否采用由业务员确认

**界面反馈**：
- 回复正文里对应的那句话被高亮，点高亮会跳到风险卡。
- 风险卡显示依据的原文摘录和来源链接。
- 业务员点"按风险提示全部修改"，第 2 轮回复补上了 FCA 说明，重新校验后是 **绿 · 可以发**。逐词对比里能看到新增的那一句。

**这次运行的质量说明**：第 1 轮回复已经如实说明了五个冲突：没有 UL、没测过 BPA、FOB 只适用于海运、做不到 20 天、不接受货到 60 天付款。所以代码规则没有报红。买家原话里的五个坑，在第 ① 步就作为"冲突"标了出来。

> 注：运行编号（run）在每次重新录制后都会变；数字以 `app/logs/calls.jsonl` 和 `docs/demo-runs/` 为准。

## 3. 第二次完整调用的标注（工作流 C，热水壶主图，违规示例图）

数据来自 `app/logs/calls.jsonl`（run `3f2748f0`），完整结果在 `docs/demo-runs/image-KET-17S_bad.json`。

**触发条件**：运营在"商品看板"点热水壶的"主图"格子，选中示例图 `KET-17S_bad.png`，点"检查这张图"。日志里的 `trigger` 字段是"上传主图"。

**输入**：一张 1500×1500 的 PNG 示意图（虚构），以及资料卡里的 `KET-17S`。

| 步骤 | 执行方 | 返回 |
|---|---|---|
| ① 像素测量 | 代码（Pillow） | 尺寸 1500×1500；四周白色比例 0%；背景不是白色，所以不估算产品占比和贴边 |
| ② 代码判定 | 代码 | IMG-03（纯白背景）判红；IMG-01、IMG-02（尺寸）通过 |
| ③ 看图审核 | 主图审核员，5 条"模型判断"类主图规则加资料卡加像素指标（2,309 字符）和图片；用量 4,709 / 909 tokens | 4 条：IMG-06 不是实拍照片、IMG-08 非随附道具（咖啡杯）、IMG-09 FREE SHIPPING · 5★、IMG-10 仿 Best Seller 徽章。每条都写了"看到了什么"，丢弃 0 条 |
| ④ 反馈 | — | 风险等级**红 · 不能发**，共 5 条；看板格子变红，"标记已上架"按钮被禁用 |

**对比**：换成合规示意图 `KET-17S_main.png` 之后（run `92fc4110`），像素指标全部通过（白色比例 100%，占比 88.5%，不贴边），只剩 1 条 IMG-06：这是插画，不是实拍照片。这条判断是对的，示例图确实是我们画的。

## 4. 异常处理

| 情况 | 处理 |
|---|---|
| 模型调用失败（网络、限流、key 无效） | 返回明确的中文错误，界面弹出提示，不显示半成品 |
| 模型返回的不是合法 JSON | 报错，不展示 |
| 模型被安全分类器拒绝（refusal） | 先由服务端 fallback 换模型重试；仍被拒就报错 |
| 合规审核这一步失败 | 代码规则的结果照常显示，标明"模型审核没有运行"，并且风险等级**不会显示为绿色** |
| 模型给出的提示没有规则编号，或原文对不上 | 由代码丢弃，界面显示丢弃了几条，原始内容可以展开查看 |
| 询盘分析里有条目找不到原文出处 | 丢弃，并显示条数 |
| 现场断网 | 用 `TRADEDESK_MODE=replay` 启动，回放录制好的结果 |
| 本机没装 Pillow | 主图的像素检查显示"未运行"，风险等级不会显示为绿色 |
| 主图审核员没写看到了什么，或规则编号不在白名单里 | 丢弃，并显示条数 |
| 主图背景不是白色 | 不估算产品占比和是否贴边：这两项估算依赖白色背景，估了只会误报 |
| 最近一次检查是红色时标记"已上架" | 代码拒绝，返回明确的中文错误 |

## 5. 数据在用户和应用之间怎么传递

```
用户输入（询盘 / 资料卡 / 中文意见）
  → 浏览器 POST /api/inquiry、/api/listing、/api/check、/api/image-check（JSON；主图用 data URL）
     商品看板：GET /api/board、GET /api/board/cell、POST /api/board/mark、GET /api/board/export.csv
  → server.py → workflows.Runner
       → llm.chat_json(system=提示词, user=输入+资料卡+规则摘要)  ← 每步写入 logs/calls.jsonl
       → checks.run_rule_checks(...)       代码规则，依据：资料卡字段 / 知识库正则与长度规则
       → checks.guard_model_findings(...)  出处守卫
  ← JSON：回复/内容、findings（每条都有 source）、dropped、risk、diff、trace
  → 浏览器渲染：高亮、风险卡、逐词对比、步骤条
```

## 6. 调用成本（实测用量）

运行 `python3 tools/cost_report.py` 会从调用日志里统计工作流 A 每条询盘的用量，结果写入 `app/eval/cost_run.json`。同一个缓存回答只算一次，回放不会重复计数。token 数是录制演示时模型实际返回的用量，输出 token 里包括思考过程。

| 项目 | 调用次数 | 8 条询盘的 token 数 | 费用（美元） |
|---|---|---|---|
| 第 1 轮（理解 + 生成 + 审核） | 3 | 10,735–16,296，中位数 14,050 | 0.087–0.150，中位数 0.135 |
| 第 1 轮 + 改一轮（共 7 条有第 2 轮） | 5 | — | 0.211–0.267，中位数 0.236 |

价格按 Anthropic 官方价目表计算（`claude-opus-5-5`：输入每百万 token 4 美元，输出 20 美元）。现场换成 Tokenhub 的模型后，报告只给出 token 数，不换算费用。业务员能省多少时间，我们没有测量过，所以不给数字。
