# 数据来源与知识库说明

## 1. 用到的数据

| 数据 | 文件 | 来源 | 合规说明 |
|---|---|---|---|
| 示例工厂与产品资料卡（4 个产品） | `app/data/products.json` | 团队自己编写 | **虚构**。价格、MOQ、产能、认证状态都是假设值，不代表任何真实企业 |
| 示例主图（4 张） | `app/static/samples/` | 团队自己画的示意图（SVG 渲染为 PNG） | **虚构**，不是产品实拍；系统会把它们判为"不是实拍照片" |
| 示例询盘（8 条） | `app/data/inquiries.json` | 团队自己编写 | **虚构**。买家、公司、邮箱都不存在；邮箱用的是 `example-kitchen.com` 这类示例域名 |
| 规则知识库（38 条） | `app/kb/rules.json` | 公开网页和官方文件（见第 3 节） | 只引用简短原文摘录并附链接；没有爬取付费数据，没有绕过任何登录或验证码 |
| 模型调用缓存 | `app/cache/` | 用上面的数据调用模型的返回结果 | 不含任何个人信息或密钥 |

工具接入真实工厂时，产品资料卡由工厂自己填写，询盘来自工厂自己的阿里国际站后台，数据只在本地处理。

## 2. 知识库怎么建的

每条规则都有以下字段：

- `id`：编号，例如 `AMZ-01`、`INC-01`
- `excerpt`：**逐字复制**的原文，25 个词以内
- `url`：原文所在页面
- `summary_zh`：中文要点
- `source_type`：primary（官方或一手来源）或 secondary（转载或二手来源）
- `verified`：是否对照原文核实过
- `fetched`：抓取日期
- `check`：怎么检查，分三种：
  - `regex`：正则，代码判断
  - `length`：长度上限，代码判断
  - `llm`：模型判断，但必须引用规则编号和原文片段
  - `image`：主图像素指标，代码测量（尺寸、白底比例、产品占比、是否贴边）
  - `vision`：模型看图判断，必须引用规则编号并写出看到了什么

**核实方法**：每条摘录都用脚本或浏览器在抓取到的页面正文里逐字查找。为了确认这种核对能发现错误，故意改了两条摘录，两条都没通过。之后又单独抽查了 3 条（ICC 的 FOB 条款、eCFR 的环保宣称、Amazon 的标题长度），全部与原文一致。后来加入的 10 条主图规则也在页面正文里逐字查找，全部找到；同时放了一条故意改过的对照摘录（"99%"），没有找到，说明这个核对能发现错误。

**`verified` 不是 `true` 的规则不参与任何检查**，单元测试会强制这一点。

## 4. 已知局限（如实说明）

- **Amazon 标题上限是 75 个字符。** 很多文章还在写 200，但 Amazon 官方页面（2026-10-26 抓取）写的是 75，适用于除沙特、埃及、土耳其、阿联酋以外的所有站点。
- **加州 65 号提案**的官方网站有验证码，我们没有绕过，所以用了 Cornell LII 转载的法规原文，标为二手来源。
- **墨西哥电器安全**：NOM-003 是否已有比 2014 版更新的版本，没有核实到；目前引用的是 2014 版。
- **阿里巴巴国际站**：没有找到公开规则页面明确禁止在回复里留站外联系方式，所以没有这条规则。代码里对应的检查没有依据，也就不运行。
- 本工具给出的是风险提示，**不构成法律或合规意见**。规则以来源页面的最新版本为准。
